What is Slurm? Slurm is an open-source workload manager or scheduler.

What it does is allow you to submit computing tasks (or jobs) to a computing cluster. A computing cluster is a collection of computers / servers (which we usually call “nodes”) together with some storage, all linked together with a fast network. The workload manager figures out when and where those jobs can run, and keeps a record of their resource usage for accounting purposes.

From a user's perspective there are three main components that you should be aware of:

First there is the login node — apart from Jupyter, this is usually your first point of contact with the cluster and the place where you will do most of your interactions. It is not a server to use for big computing tasks; rather, it's a place for administrative tasks such as submitting jobs, editing scripts and light management of data. The login node is shared with all the users of the cluster — any misuse impacts others negatively — so we monitor it closely and are quite strict about how it's used.

Second there is Slurm itself, which has 3 key functions:
  • Slurm allocates access to resources for users. In other words this is reserving memory and CPU resources on the compute nodes for specific jobs.
  • Slurm provides a framework for starting, executing, and monitoring work or jobs. These are the commands I will cover a little bit later.
  • Slurm manages a queue for pending work. When you submit a job, it first sits in a queue and waits for its turn to run. In Slurm these queues are called partitions and there are several different ones you can choose from — more on that later.
Finally there are the compute nodes — these are bigger servers and the place where computing jobs are run. Once you're running something on a node, the resources you've requested are allocated to you. This means that nobody else can interfere with the running of your software, but the flip side of that is that you should be as accurate as possible when specifying those resources. This is covered in more detail in Session 2.

Slurm Quick Start User Guide
Every Slurm job follows the same four steps: write a script containing the commands you want to run, submit it with sbatch, monitor it with squeue, and then inspect the output files it produced.

Everything else in this session — resource requests, partitions, containers — is an extension of this basic loop. If you keep this picture in mind, the rest of the slides will slot into place.

And if you submit something by mistake, scancel with the job ID removes it.

Slurm Quick Start User Guide
First one has to connect to the login node — generally with the `ssh` command if you're working on Linux or macOS, or some SSH client on Windows.

Once you have landed on the login node, these are the basic Slurm commands that map onto the four-step workflow from earlier. They allow you to submit and monitor jobs as well as get information about the state of the cluster. I'll demo all of these commands later, but here is a quick rundown.

Sinfo gives you information about the partitions (sometimes called queues). It shows you the number of nodes available and their state: are they free, partially used or fully allocated to jobs.

Sbatch is how you submit a regular job on the cluster. When you run it (and there are no problems in your script) it gives you a job ID.

Squeue gives you information about jobs that have been submitted to the cluster and have not finished running yet. With the “-u” filter it shows only your own jobs; without it you see the whole cluster's queue.

Scancel, with a job ID, cancels a queued or running job.

There are a handful of other ways to submit jobs but these will be covered later in one of the advanced training sessions.

Bash Scripting
So what is a job script? A job script is (usually) a simple Bash script that describes what resources your job requires and then the steps your job should take in order to process your data.

This is (almost) the most simple script you could have. The very first thing is this shebang line, which tells Slurm to interpret this script using the Bash scripting language — unless you're doing something pretty unusual, all your scripts will have the same first line.

The next lines are simply the commands that will be run. In this case we're using the “module” system and we're telling it to use Python 3.12.9. In other words this makes Python 3.12.9 available to use. And then we run the “hello_world.py” script using that Python.

Note that at this point it's just a Bash script — there is nothing Slurm-specific in it yet. We can submit this job, Slurm will send it to a compute node and run it. I'll demonstrate that shortly.

But Slurm is in charge of allocating resources, and the question you might be asking is — how does it know which queue to run on? How many CPUs to use? How much memory should be allocated?

Well, there are a bunch of defaults…

What Slurm assumes if you don't specify resources

Resource Default
CPUs 1

#SBATCH directives in your job script override these defaults. Note the difference: --mem=4G requests 4 GiB for the job on each allocated node, while --mem-per-cpu=4G requests 4 GiB for each allocated CPU.
sbatch parameters
And here they are.

By default, if not otherwise specified, a job has a time limit of 3 hours and uses 1 CPU on 1 node. It runs on the Main partition against your default account.

The default memory scales with the number of CPUs you request — on Main it is 3 GiB per CPU (the HighMem and GPU partitions have larger per-CPU defaults, which we'll see in the reference table at the end).

When you override the defaults, be aware of the difference between --mem, which is per node, and --mem-per-cpu, which is per CPU. For single-CPU, single-node jobs — most of what we do today — they amount to the same thing, but for parallel jobs the distinction matters.

Now let's look at what a script with Slurm parameters set explicitly might look like.

A minimal production job


#!/bin/bash
#SBATCH --job-name=tutorial2_python_module
#SBATCH --time=00-00:01:00
#SBATCH --mem=1G
#SBATCH --output=python_module-%j.stdout
#SBATCH --error=python_module-%j.stderr

module add python/3.12.9
python hello_world.py
%j is replaced with the Slurm job ID, so each job gets a distinct log file.

Submit the job: 

sbatch maximal_python.sbatch
Slurm sbatch documentation
This is the same Bash script as before, but now with a set of #SBATCH lines that Slurm interprets. These lines explicitly declare settings and override the defaults from the previous slide.

Briefly, the parameters:

job-name: a name for your job, which appears in squeue.
time: the expected duration — overestimate a bit to allow extra room.
mem: how much memory the job may use.
output and error: where standard output and standard error are logged. The %j is replaced with the job ID, so each run gets its own distinct log files rather than overwriting the previous ones.

These five settings — name, time, memory, output and the command itself — are all a typical production job needs.

Optional settings — and containers


#!/bin/bash
#SBATCH --job-name=tutorial2_R_container
#SBATCH --time=00-00:01:00
#SBATCH --mem=4G
#SBATCH --output=R_container-%j.stdout
#SBATCH --error=R_container-%j.stderr
# #SBATCH --partition=Main
# #SBATCH --mail-user=your@email_address
# #SBATCH --mail-type=BEGIN,END,FAIL,TIME_LIMIT_80
# #SBATCH --account=your_project_account

singularity exec /software/common/containers/RStudio2023.06.1-524-R4.3.1.sif Rscript hello_world.R

Submit the job: 

sbatch maximal_R.sbatch
Slurm sbatch documentation Software environments
A few more settings you may want, shown here commented out — uncomment and edit them if you need them. Leaving placeholder values like an unedited email address or account in place can cause your submission to fail, which is why the tutorial files ship with these lines commented out.

partition: select a partition based on your use case; if omitted, the default is Main.

mail-user and mail-type: receive notifications when your job starts, ends, fails, or times out. TIME_LIMIT_80 notifies you when your job has used 80% of its time limit, allowing you to request more time if needed by contacting the ilifu helpdesk.

account: the account identifies the project against which your usage is recorded. Use the account associated with your work — if you only belong to one project, the default is already correct.

And note the command at the bottom: this time we run the R script inside a Singularity container, which provides a reproducible R environment — an alternative to the module system we used for Python.

Finally, sbatch submits the job. Remember, jobs run on compute nodes, not the login node, so you can continue working after submitting.

Choosing where your job should run

Partition Use it for
Main Most batch and production jobs (the default)
Devel Short interactive testing and debugging
HighMem Jobs that require more memory than Main provides
GPU GPU-accelerated software
Jupyter Browser-based interactive analysis
A partition is a group of nodes with a shared purpose — it is what you choose with --partition. Exact node counts and hardware specifications are in the reference table at the end of this presentation.
Available Resources
Now that you've seen the --partition setting, here is how to choose one.

The default partition is Main, and unless you explicitly need something else, this is probably the one you'll want to use. It is where most stable and computationally intensive jobs are executed. (By stable I mean the code isn't changing — it is an established process that only differs in input and output.)

The Devel partition is a development space for testing new software, building workflows, and debugging — it supports interactive jobs, which are explained in a later session.

The HighMem partition is designed for single, high-memory jobs that can't be split up — we have 8 HighMem nodes, most with about 500 GiB of RAM and the largest with 96 cores and about 1.5 TiB. We'll dive deeper into this topic in a later session.

The GPU partition has 7 nodes with NVIDIA GPUs for GPU-accelerated software.

Then there's the Jupyter partition, which you only ever implicitly use, if you're using Jupyter.

While many users use Jupyter as their primary interface with the compute resources, we do, as a general rule, prefer users to submit batch jobs to the Main, HighMem or GPU partitions, as this tends to result in more efficient use of resources. Interactive jobs such as Jupyter tend to have long periods where resources sit idle.

Best practices

ilifu is shared by many researchers. Accurate requests help your jobs start sooner and make the cluster work better for everyone.

✅ Do

  • Use sbatch for production work
  • Start with one CPU unless the software supports parallel execution
  • Request slightly more time and RAM than a measured test run needs
  • Check job logs before requesting additional resources
  • Use /scratch3 for temporary data and clean up when finished
  • Use Singularity containers or modules for software
  • Use transfer.ilifu.ac.za for data transfers

❌ Don't

  • Run compute-intensive commands on the login node
  • Place large files in /users (home dir)
  • Use scp/rsync on the login node
  • Substantially over-request CPUs, RAM, or run time
Best Practices
As we conclude, here are the main points to remember and some things to avoid:

Do's:
Use sbatch for running jobs and accurately estimate your job's resource requirements — do a small test run, check the logs, and request slightly more than it used.
Keep your directories clean by removing unneeded files, use /scratch3 for temporary data, and avoid storing large files in your home directory.
Use Singularity containers or modules for software execution and use the dedicated transfer server for data transfers.

Don'ts and what to avoid:
Refrain from running heavy processes or software on the login node.
Avoid using scp/rsync for data transfers on the login node.
Avoid substantially over-requesting resources — idle allocated CPUs and memory are unavailable to other researchers.

By following these guidelines you can make the most of the ilifu cluster and ensure an efficient, hassle-free experience.

A few things worth noticing:

The default number of CPUs is 1 for all the partitions.

There is a range of maximum cores per node, even within the Main partition. At the lower end it's 32, while at the top end HighMem has a node with 96 cores.

The default memory is about 3 GiB per CPU on the Main partition, 15 GiB per CPU on HighMem and 7 GiB per CPU on the GPU nodes.

And note that the GPU partition has a shorter maximum wall-time of 3 days — for longer GPU workloads, checkpointing is recommended, or contact support with a motivation.
