Available Resources
A quick review of ilifu's resources. A computing cluster is a collection of servers or nodes (those terms can be used interchangeably) that are combined to work together in a way that is more powerful than the sum of the individual parts. The parts are: a login node (your main interface to the cluster); the compute nodes (grouped into partitions, also known as queues); permanent shared storage; and a network connecting it all together. Today I'll be using the "Main" partition, whose nodes are largely 32-core servers with between 230 and 250 GiB of RAM, depending on the specific node you end up on. We have something like 8 PiB of shared storage on our Ceph cluster. The network deserves a special mention because it matters for this session: our nodes are connected by Gigabit Ethernet. It has high bandwidth — it can move a lot of data quickly — but it is not a low-latency network like the InfiniBand you might find at the CHPC. That means it is not well suited to workloads that need a lot of very quick back-and-forth communication between nodes. I'll come back to this when we look at multi-node jobs. The full partition and node specifications are on a reference slide at the end — you don't need to memorise them.

What is Parallelism?

Parallel computing performs multiple parts of a computation at the same time.
It helps only when the work can be divided and the cost of coordinating the workers is small enough.
  • A cluster includes many connected nodes, each with its own RAM & CPUs
  • A node = single computer / server / VM / machine / box
  • The work is partitioned into smaller units of work, often by splitting the dataset
Parallelism (Wikipedia)
Modern data sets in both bioinformatics and astronomy have grown so large that it's becoming increasingly rare to be able to do meaningful research on our own PCs or laptops. We are usually limited by the memory, CPU or storage available on these devices, and that's when we need a computing cluster — and where we can really take advantage of parallelism. Parallel computing simply means performing multiple parts of a computation at the same time. The catch is that it only helps when the work can be divided, and when the cost of coordinating the workers doesn't swallow the benefit. An astronomy example: the raw data from a radio telescope such as MeerKAT can be partitioned into multiple spectral windows (SPWs), and each SPW processed simultaneously — this is what the processMeerKAT pipeline does during signal processing. A bioinformatics example: aligning sequencing reads to an existing genome — the reads can be processed independently, making the workload well suited to parallel execution. There is also a harder class of problem where the parts are highly dependent on each other — for example a protein-folding simulation, where we break a volume into smaller volumes but must constantly account for interactions at the boundaries. Keep that example in mind: it's the kind of communication-heavy workload that behaves very differently on our network.

Serial vs Parallel — the serial baseline

One step at a time


grades = [50, 65, 82, 79, 48, 72]
total = 0
for grade in grades:
    total = total + grade
average = total / len(grades)

All instructions run sequentially on a single CPU.

Execution trace


grades = [50, 65, 82, 79, 48, 72]
total = 0
total = 0 + 50 = 50
total = 50 + 65 = 115
total = 115 + 82 = 197
total = 197 + 79 = 276
total = 276 + 48 = 324
total = 324 + 72 = 396
average = 396 / 6 = 66
Let's consider a very simple computation: the average of a set of grades. A serial program does one step at a time — six additions, one after the other, then a division. Only one CPU does any work, no matter how many the machine has. This is our baseline. The question is: how do we share this work between several workers?

Serial vs Parallel — split, process, combine

Each worker sums its chunk


grades = [50, 65, 82, 79, 48, 72]
chunk = len(grades) // N  # choose N=3 workers
grades_part = grades[worker_id*chunk:(worker_id+1)*chunk]
partial_sum = sum(grades_part)
average = sum(all_partial_sums) / len(grades)

All 3 workers process their chunk simultaneously; one worker combines the partial sums.

Execution trace


grades = [50, 65, 82, 79, 48, 72]
# Split: each worker takes 2 consecutive grades
W0: grades_part = [50, 65]
W1: grades_part = [82, 79]
W2: grades_part = [48, 72]
# Process: all workers sum simultaneously
W0: partial_sum = 115
W1: partial_sum = 161
W2: partial_sum = 120
# Combine (W0):
average = (115 + 161 + 120) / 6 = 66

Divide-and-conquer algorithm
The parallel version has three phases: split the data into chunks, let every worker process its own chunk at the same time, then combine the results. Note that each worker computes a partial sum, not a partial average. Combining partial sums works no matter how the data was divided; averaging the workers' averages would only be correct if every chunk had exactly the same size. Summing partial results like this is called a reduction, and it's exactly what the MPI.Reduce call does in the tutorial's simple_mpi.py — so this little example is the same shape as the real demo we'll run later. The split-process-combine pattern at the bottom is the shape of almost all data parallelism.

More resources are not enough

Parallelism only pays off when all of these hold:

  • Hardware must provide concurrent resources — multiple CPU cores (some nodes also have GPUs)
  • Software must expose parallel work — code written with MPI, threading or OpenMP in mind
  • Coordination has a cost — splitting work, communicating, combining results all take time
  • The workload must be large enough to repay that cost
Running ordinary serial software on a node with more cores will not make it faster — the software has to be written (and configured) to use them.
So compared to a serial process, parallelism has several requirements, and it's worth spelling them out because the most common misconception we see is "I requested more CPUs, why isn't my job faster?". First we need multiple resources available simultaneously — many CPU cores. On a single core, only one instruction stream executes at any instant (the operating system can time-slice many processes, but they take turns). Second, the software must have been written to take advantage of those resources. You cannot take an arbitrary piece of software and expect it to run faster on a machine with more cores. Third, coordination — the mechanism by which the parts of the program communicate — takes time. Typically one part of the software is in charge of the overall plan: telling the other parts which data to analyse and combining results at the end. This is achieved with frameworks or libraries such as MPI (Message Passing Interface), traditional threading, or OpenMP (Open Multi-Processing, a framework that makes threading easier). And fourth, the problem has to be big enough that the time saved computing outweighs the time spent coordinating. One more hardware note that matters on ilifu specifically: we do not have a low-latency network like the CHPC's InfiniBand. Latency is the time it takes for even a small message to get from one node to another. If you have the kind of problem with lots of communication between nodes — like the protein-folding example — spreading it across multiple nodes can actually slow it down, because you spend your time waiting for messages rather than computing. For those problems you're better off at a facility with InfiniBand. Our network does have high bandwidth though: messages take a while to get going, but they can be big, so we can move a lot of data quickly.

Single-node vs Multi-node Parallelism

Single-node (shared memory)

  • Distributes work over many CPUs within one node
  • Threads / OpenMP — workers share the node's memory directly
  • MPI also works within one node (ranks communicate via shared memory)
  • GPU acceleration — a separate execution model, also single-node
Node (32 CPUs)
Core 1 · Core 2 · … · Core 32
shared memory — fast communication

Multi-node (distributed memory)

  • Distributes work over many tasks across 2+ nodes
  • Requires MPI: mpirun, srun, mpicasa (CASA)
  • Hybrid parallelism: MPI + OpenMP / MPI + GPU
Node A
Tasks 1–4
⟷ network
Node B
Tasks 5–8
⚠ ilifu does not have InfiniBand. Network latency between nodes is higher than at e.g. the CHPC. For communication-heavy workloads, multi-node MPI adds overhead that can make jobs slower than single-node — the live demo will show this.
The central distinction on this slide is shared memory versus distributed memory. Within a single node, all the cores can see the same memory. Multi-threaded code — usually written with threads or OpenMP — works well here because the parallel parts communicate directly through that shared memory; nothing goes over a network. GPUs are a different execution model again: they're used where you run exactly the same code on many pieces of data simultaneously, whereas threads can each be doing somewhat different things. MPI is not only for multiple nodes — MPI ranks on the same node communicate through shared memory too, and in fact most of our demo runs MPI on a single node. What MPI adds is the ability to go beyond one node: Slurm allocates the machines and tells the job what memory and CPUs are available, and MPI distributes the work across them and combines the results. Two practical notes for later: first, if you use Singularity, a container is an isolated software environment — it shares the host's kernel, it is not a separate machine — but you still need the MPI version inside the container to match the version outside it. Second, when you mix MPI and threads, where the ranks and threads are placed (binding) is a separate concern from how many you request — benchmark before trusting a layout.

Parallelism in Slurm

Type --nodes --ntasks --cpus-per-task Application setting
Serial 1 1 1 None — the default
OpenMP / Threading 1 1 8 OMP_NUM_THREADS=8 or e.g. --threads 8
MPI (single-node) 1 8 1 mpirun launches 8 ranks
MPI (multi-node) 2 8 (4 per node) 1 mpirun — cross-node overhead; benchmark first
Hybrid MPI+OpenMP 2 2 (1 per node) 4 mpirun + OMP_NUM_THREADS=4
Tip: On ilifu, keep --nodes=1 when the job fits on one node — communication can then use shared memory rather than the inter-node network. Use multiple nodes when you need more cores or memory than one node provides, and benchmark the difference.
By default a job in the cluster has a single CPU allocated to it. That's what you'd use for code with no parallelism — perhaps some pre-processing where everything must happen sequentially. The next level is threading or OpenMP: one task, multiple CPUs per task, all on one node. Requesting the CPUs is only half the story — you usually must also tell the software how many threads to use, with OMP_NUM_THREADS for OpenMP software or a command-line option for others. That's the last column of this table, and it matters because some software assumes all the cores on the machine are available, while your job is restricted to its allocation. An MPI job uses multiple tasks — on one node or spread across several. The constraint to remember is per node: tasks per node times CPUs per task must fit within the CPUs of the node — 32 on most of our Main nodes, with a handful larger. The hybrid row combines both: here, two nodes, one rank per node, four threads per rank — eight cores in total, matching the tutorial's hybrid demo.

One correction worth making explicitly, because the distinction trips people up: --cpus-per-task allocates CPU cores to each task; it does not create threads. Slurm — Serial and Multi-CPU Jobs

Serial job (1 CPU)

#SBATCH --nodes=1
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=1

python myscript.py

OpenMP / threading job (8 CPUs)

#SBATCH --nodes=1
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=8
#SBATCH --mem-per-cpu=1GB

export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
./my_threaded_program

When to use each

  • Serial: code has no internal parallelism — increasing CPUs or nodes will not help
  • Threaded: software runs multiple threads on one node — configure it with the control it supports: OMP_NUM_THREADS for OpenMP code, a program option like bwa -t 8 / STAR --runThreadN 8, or a library setting like OPENBLAS_NUM_THREADS for NumPy's BLAS backend

Watch out for

  • Always set the thread count explicitly — some software defaults to all cores on the node, not just your allocation
  • Most Main nodes have 32 CPUs — and the maximum will not always give maximum speedup; test with fewer cores first
These snippets show only the resource layout — a complete script also needs --time, --mem, --output/--error and a job name, as covered in Session 1.
Two single-node layouts. The serial job is Slurm's default shape: one node, one task, one CPU. The threaded job requests eight CPUs for its single task, and then — the crucial line — tells the software to actually use them. Using the SLURM_CPUS_PER_TASK environment variable keeps the thread count in sync with the allocation if you later change the request. The one sentence to remember from this slide: requesting CPUs does not make software parallel — you must also configure the software, with whatever control it supports.

Slurm — Multi-task (MPI) Jobs

Using --ntasks (Slurm allocates nodes)

#SBATCH --ntasks=8
#SBATCH --cpus-per-task=1
#SBATCH --mem-per-cpu=1GB

module add openmpi/5.0.3
mpirun python simple_mpi.py

Using --ntasks-per-node (you control layout)

#SBATCH --nodes=1
#SBATCH --ntasks-per-node=8
#SBATCH --cpus-per-task=1
#SBATCH --mem=8GB

module add openmpi/5.0.3
mpirun python simple_mpi.py

Key differences

  • --ntasks=8 — Slurm decides how to spread 8 tasks across nodes; may use multiple nodes
  • --ntasks-per-node=8 — you specify exactly how many tasks per node; set --nodes too
  • mpirun reads the Slurm allocation — no -np needed (srun can also launch MPI programs)

On ilifu

  • Prefer --nodes=1 --ntasks-per-node=8 to stay on one node
  • Avoids accidental multi-node allocation that adds latency
  • Tasks × CPUs per task must fit the node (32 CPUs on most Main nodes)
Two ways to request an MPI job. With --ntasks alone, Slurm places the 8 tasks wherever it finds free CPUs — possibly across several nodes. With --nodes plus --ntasks-per-node you pin the layout down. On ilifu, because of the network we discussed, prefer the explicit form that keeps the ranks on one node when they fit. Notice that mpirun gets no process count: it reads the allocation Slurm made and launches one rank per task automatically. The script here is exactly the tutorial's — simple_mpi.py, with openmpi/5.0.3 — so what you see on the slide is what you'll run in the demo.

Slurm — Multi-node and Hybrid Jobs

Multi-node MPI

#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --cpus-per-task=1
#SBATCH --mem=4GB

module add openmpi/5.0.3
mpirun python simple_mpi.py

2 nodes × 4 tasks each = 8 MPI ranks.
--mem is per node, so 2 × 4 GB total RAM.

Hybrid MPI + OpenMP

#SBATCH --nodes=2
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=4

module add openmpi/5.0.3
export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
mpirun ./hybrid_sum

2 nodes × 1 rank × 4 OpenMP threads = 8 cores in total.

Remember: Inter-node communication is slower than intra-node on ilifu. Always benchmark before scaling to multiple nodes.
On the left, the multi-node MPI layout the demo uses: two nodes, four ranks on each, eight ranks in total. Note that --mem is per node. On the right, the hybrid layout from the tutorial's hybrid_sum demo: one MPI rank per node, four OpenMP threads inside each rank. The export line is essential — without it the ranks are allocated four CPUs each but OpenMP is never told to use them. A caution for hybrid jobs specifically: how the ranks and their threads are bound to physical cores can dominate performance, and the defaults are not always sensible. If your hybrid job shows no speedup over serial, suspect binding before blaming the code — and benchmark, which is exactly what the tutorial's job scripts let you do.

Full results in the tutorial README
Example results from a previous run — your times will vary a little, but the pattern is stable. Three observations. First, parallelism works: 8 ranks run the job about five times faster than one. Second, speedup is not linear: 4 ranks give roughly 3×, not 4×; 8 ranks give roughly 5×, not 8×. Efficiency drops as we add workers, because coordination overhead grows while each worker's share of the work shrinks. Third — the punchline — the same 8 ranks split across two nodes are slower than 8 ranks on one node. We added no work and no workers; we only changed how the ranks communicate: over the network instead of through shared memory. For this small, chatty workload, that overhead exceeds any benefit. Note what this experiment does and doesn't show: it demonstrates communication overhead — it does not say multi-node jobs are useless. If your job needs more memory or more cores than one node has, multiple nodes are exactly the right tool; benchmark to see whether the extra resources outweigh the overhead.

Best Practices for Parallel Jobs

✓ Do

  • Confirm the software actually supports the parallel model before requesting CPUs
  • Start on one node and benchmark several task / thread counts
  • Keep tasks × CPUs-per-task within one node's CPUs where possible
  • Measure speedup and resource efficiency (seff — next tutorial)
  • Use multiple nodes only when memory, CPU demand or measured scaling justify it
  • Use sbatch for unattended or long-running work

✗ Don't

  • Assume more CPUs automatically means faster — test it
  • Spread communication-heavy jobs across nodes without benchmarking first
  • Substantially over-request CPUs, memory or run time — request what a measured test run needs, plus a margin
  • Rely on interactive sessions for long jobs — interactive srun / sinteractive is for short testing and debugging (Session 2)
General cluster etiquette — login-node use, data transfers, storage cleanup — is covered in Session 1 and the Best Practices docs.
Best Practices docs
These are the practices that specifically change how you run parallel jobs. The workflow to internalise: confirm the software can use the resources, start small on one node, measure, and only then scale — and only across nodes when the memory or CPU demand, or your own measurements, justify it. Accurate, realistic requests also help your jobs start sooner: a job with a modest, honest time limit is easier for Slurm to backfill into gaps in the schedule.
